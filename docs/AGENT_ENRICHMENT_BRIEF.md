## 1. Что заполняем, по приоритету

Приоритет не косметический — он отражает, что блокирует продукт.

### Приоритет 1 — `menu` (блокирует интеграцию с SŌMA)

Сейчас: **0 из 456**. Без этого поля сомелье не с чем сопоставлять профиль
вкуса — мы знаем, где магазин, но не знаем, можно ли прочитать его витрину.

Работаем по 316 открытым точкам, у которых есть сайт (`operationalStatus:
"OPEN"` и `contact.website != null`).

Как определить платформу — по тому, что реально грузится на странице заказа
(iframe, script, ссылка кнопки «Order online» / «Shop now» / «Menu»):

| Признак в разметке | `menu.provider` |
|---|---|
| `dutchie.com`, `embed.dutchie.com` | `DUTCHIE` |
| `iheartjane.com`, `menu.iheartjane.com` | `IHEARTJANE` |
| `getmeadow.com`, `meadow.menu` | `MEADOW` |
| `blaze.me`, `ecommerce.blaze.me` | `BLAZE` |
| `treez.io`, `*.treez.io` | `TREEZ` |
| ведёт на `leafly.com/dispensary-info/...` | `LEAFLY` |
| ведёт на `weedmaps.com/dispensaries/...` | `WEEDMAPS` |
| меню на собственном домене, без сторонней платформы | `PROPRIETARY` |
| платформа опознана, но её нет в списке | `OTHER` |
| сайт есть, меню онлайн нет | `NONE` |
| сайт не открылся / определить не удалось | `null` |

При `OTHER` обязательно впишите настоящее название платформы в
`verification.notes` строкой вида `menu platform: posabit`. Если одно и то же
имя встретится больше десяти раз — это сигнал расширить enum, вынесите его в
отчёт отдельно.

Заполняйте также `menu.menuUrl` (прямая ссылка на меню, не на главную) и
`menu.menuIsPublic` — `true`, только если меню читается без логина и без
подтверждения возраста, ставящего куки-стену. Возрастная заглушка, которая
пропускает по кнопке «мне 21», не считается закрытым меню.

**Чего не делать:** не заказывать, не регистрироваться, не обходить возрастные
и антибот-заглушки, не парсить содержимое меню (товары, цены, остатки). На этом
этапе нам нужен только факт платформы и адрес меню.

### Приоритет 2 — `geo`

Сейчас: **0 из 456**. Без координат нет карты, а карта — основной способ
пользоваться справочником в городе.

Два бесплатных геокодера, оба без ключа:

- **US Census Geocoder**, пакетный режим, до 10 000 адресов за раз:
  `https://geocoding.geo.census.gov/geocoder/locations/addressbatch`
  (`benchmark=Public_AR_Current`).
- **NYC GeoSearch** (только пять боро, точнее для города):
  `https://geosearch.planninglabs.nyc/v2/search?text=...`

**Про честность `precision` — читайте внимательно.** Census возвращает результат
интерполяцией по диапазону номеров вдоль улицы. Это **`INTERPOLATED`**, а не
`ROOFTOP`, даже когда `matchType` равен `Exact`. `ROOFTOP` ставится только если
геокодер прямо заявляет попадание в здание. `CENTROID` — если попали лишь в
центр ZIP или города; такой результат для карты почти бесполезен, помечайте
честно. `geo.source` — конкретное имя сервиса, не «geocoder».

Координаты обязаны попадать в bbox `lat 40.4…41.4`, `lng −74.3…−73.4` —
валидатор это проверяет. Промах означает, что геокодер ушёл не туда: оставьте
`geo: null` и запишите в `warnings`.

### Приоритет 3 — `contact.phone`

Сейчас: **0 из 456**. Берём с сайта самого диспансера. Формат строго
`+1-212-555-0100` — валидатор проверяет по маске. Номер из Google Maps
допустим, но помечается в `verification.notes`.

Если на сайте несколько номеров (магазин и корпоративный офис) — берите тот,
что указан на странице этой конкретной точки. У сетей с несколькими адресами
это разные номера, не копируйте один на всех.

### Приоритет 4 — `services` и `address.neighborhood`

Из реестра уже пришли `inStorePurchase`, `delivery`, `servesAdultUse`. Их **не
перезаписывать** — они реестровые.

Остальные (`pickup`, `curbside`, `adaAccessible`, `onsiteConsumption`,
`servesMedical`, `acceptsDebit`, `acceptsCredit`, `cashOnly`, `atmOnSite`,
`parking`) заполняются только при явном утверждении на сайте. «Не написано» —
это `null`, а не `false`. Формулировка «we accept all major cards» — это
`acceptsCredit: true`; отсутствие раздела об оплате — `null`.

`neighborhood` — только если уверены. «Bronx» в поле города не делает район
известным.

## 3. Правила работы с существующим файлом

Вы редактируете **уже валидный** датасет. Отсюда несколько жёстких требований:

- **`id` не меняются никогда.** Они уже опубликованы как URL страниц.
- **`licenseNumber` не меняются.** Это ключ, по которому ingest сопоставляет
  записи при следующем прогоне.
- **`verification.status` не понижается.** Все 456 записей —
  `VERIFIED_OFFICIAL`, и обогащение это не отменяет: источник лицензии
  остался прежним.
- **`verification.confidence` пересчитывается.** `HIGH` — заполнены адрес,
  статус, часы, телефон и меню, расхождений нет. `MEDIUM` — часть обогащения
  отсутствует. Сейчас 309 `HIGH` / 147 `MEDIUM`; после прохода доля `HIGH`
  должна вырасти, и если она не выросла — объясните почему.
- **Источники добавляются, а не заменяются.** У записи остаётся реестровый
  источник плюс новые: `BUSINESS_WEBSITE`, `MENU_PLATFORM`, `MAPS`.
  У каждого свой честный `retrievedAt`.
- **`lastUpdated`** обновляется у тронутых записей.
- Каждое расхождение между сайтом и реестром — строка в `warnings`, а не
  молчаливый выбор в пользу одного из них.

Коллекторы написаны и отработали (6 зелёных прогонов). **Но фаза не закрыта:**
evidence лежит только в артефактах CI со сроком хранения 7 дней, а
`data/dispensaries.json` не изменён ни на байт.

Недостающее звено дописано за вас — `scripts/enrichment-apply.py`. Он переносит
evidence в датасет и следит за правилами, которые иначе легко нарушить при
слиянии: реестровые флаги услуг не перезаписываются данными с сайта, `null`
никогда не превращается в `false`, `id` и `licenseNumber` неизменны,
`verification.status` не понижается.

Workflow `enrichment-debt-audit.yml` теперь замыкает цикл целиком:
собрать → применить → провалидировать → закоммитить.

**Что осталось сделать:** запустить workflow (push в ветку или
`workflow_dispatch`) и проверить результат. Один прогон закрывает фазу.
